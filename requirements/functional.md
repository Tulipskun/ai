# ข้อกำหนดด้านการทำงาน

REQ-001 — Harness รับ canonical input ได้โดยไม่ขึ้นกับ transport

REQ-002 — CLI และ Discord สามารถใช้ Harness/Agent runtime เดียวกันได้

REQ-003 — แต่ละ session มี state แบบถาวรที่แยกจากกัน และสามารถกู้คืนได้หลัง process restart

REQ-004 — Agent สามารถทำลูป model → tool call → tool result → model จนกว่าจะไม่มี tool call เหลือ

REQ-005 — ความล้มเหลวของ tool ต้องถูกส่งกลับมาในรูปแบบ tool result เพื่อให้ Agent สามารถกู้คืนได้โดยไม่ทำให้ทั้ง turn ล้มเหลว

REQ-006 — รูปแบบ request/response เฉพาะของ provider ต้องถูกแยกไว้หลัง adapter และแปลงผ่าน canonical SDK model

REQ-007 — การค้นหา provider model ต้องใช้ catalogue ของ provider ที่ดึงจากระบบจริง และเมื่อ refresh สำเร็จต้องแทนที่ข้อมูล catalogue เดิมที่ค้างอยู่

REQ-008 — การ retry ต้องใช้ API key ของ session ที่เลือกไว้ และห้ามเปลี่ยน key โดยอัตโนมัติ

REQ-009 — output แบบ streaming จะต้องไม่ถูก replay โดยอัตโนมัติหลังจากเริ่มส่ง output แล้ว

REQ-010 — Browser automation ต้องใช้งานได้ผ่าน Go CDP implementation ที่อยู่ในตัว โดยไม่ใช้ Playwright หรือ Node.js worker รองรับ Firefox ESR 140 ผ่าน Remote Agent CDP (`--remote-debugging-port` + `/json/version` polling หา webSocketDebuggerUrl) นอกเหนือจาก Chrome/Chromium/Edge โดยไม่ใช้ geckodriver/Marionette

REQ-011 — Runtime configuration ต้องเป็นแบบไฟล์ภายใต้ layout `~/.local/share/ai` ที่กำหนดไว้ และไม่ต้องใช้ environment variable ในการตั้งค่า

REQ-012 — Project requirements ต้องเก็บอยู่ใน repository และถือเป็น source of truth สำหรับงานของโปรเจค

REQ-013 — ก่อน implement request ใหม่ AI ต้องตรวจสอบ repository requirements และบันทึก specification change ที่ request นั้นทำให้เกิดขึ้น

REQ-014 — เมื่อสร้าง software project ใหม่ AI ต้องสร้างและเติมข้อมูลใน `requirements/` ของ project นั้นก่อนเริ่ม implementation ในส่วนสำคัญ

REQ-015 — การเปลี่ยนแปลงโค้ดต้องรักษาความรับผิดชอบของแต่ละ module ให้ชัดเจน และต้องเพิ่มหรือแก้ functionality ใน module ที่รับผิดชอบโดยตรง เว้นแต่มีการเปลี่ยน architecture ที่บันทึกไว้อย่างชัดเจน

REQ-016 — เมื่อเปิด planning, Main Agent จะได้รับเฉพาะ planning tools, tools สำหรับ orchestration ของ sub-agent และ tool สำหรับส่งต่อ opaque file reference (ชื่อ/ชนิด/ขนาด/relative path ภายใน file store) เท่านั้น ไม่ใช่เนื้อหาไฟล์ และต้องปฏิเสธ execution call โดยตรง รวมถึงหลังจากบันทึกแผนแล้วด้วย Main Agent ห้ามได้รับ byte stream, base64, MIME data หรือเนื้อหาภายในไฟล์ผ่านช่องทางใด ๆ รวมถึงผ่าน tool result ของ orchestration ด้วย file reference ต้องถูก resolve โดย worker agent หรือ transport module เท่านั้น ค่าเริ่มต้นของคำสั่ง Main Agent ต้องมอบหมายการตรวจสอบโปรเจคและการดำเนินงาน แทนการสั่งให้ Main Agent ใช้ worker tools โดยตรง โดยความพยายามต้องได้สัดส่วนกับความซับซ้อนของงาน: งานที่ต้องใช้ repository context เท่านั้นจึงต้องมีขั้นตอน investigation แยกต่างหาก งานเล็กน้อยที่ไม่ต้องใช้ repository context (เช่น สร้าง/ลบไฟล์เดียว) ต้องใช้แผนขั้นเดียวที่สั้นที่สุดโดยข้าม investigation แยก และแผนทุกขนาดต้องมีจำนวน step น้อยที่สุดที่ครอบคลุมเป้าหมาย และทุก turn ของ Main Agent เมื่อมีแผนอยู่แล้ว system prompt ต้องแนบ checklist ปัจจุบัน (ลำดับ step พร้อมสถานะ pending/ready/running/awaiting_review/failed/completed) เพื่อให้ Main Agent เป็นผู้ถือภาพรวมและตรวจรายการด้วยตนเอง (CHANGE-022) ข้อความที่ไม่ใช่งาน (ทักทาย/ขอบคุณ/acknowledgement/คำถามที่ตอบได้ตรงจากบทสนทนาโดยไม่ใช้ tools, repository context หรืองานที่ต้องทำ) ให้ Main Agent ตอบตรงทันทีโดยไม่สร้างแผน ไม่ delegate และไม่ investigate (CHANGE-032)

REQ-017 — เมื่อ `DisablePlanning: true`, execution/worker agent ต้องคง system prompt และ execution tool definitions ที่ได้รับมาไว้ทั้งใน turn ปกติและ streaming turn รวมถึงตอนทำต่อหลัง tool result; Harness ห้ามแทรกข้อจำกัดของ Main Agent หรือ planning/delegation tools เข้าไป ค่าเริ่มต้นของคำสั่ง sub-agent ต้องจำกัดงานให้อยู่ใน scope ที่ได้รับ ห้าม delegation ต่อ และห้ามสื่อสารกับ end user โดยตรง และต้องรายงานสิ่งที่ตรวจพบ/ผลลัพธ์ให้ planner การตรวจสอบผลต้องใช้วิธีที่น้อยที่สุดแต่เพียงพอ: คำสั่งเดียวที่พิสูจน์ผลลัพธ์ได้ (หรือ shell line เดียวที่รวมการตรวจที่เกี่ยวข้อง) ห้ามทำซ้ำรายการที่เทียบเท่ากัน (เช่น ls/wc/cat/stat ไฟล์เดียวกัน) เมื่อพิสูจน์ผลได้แล้ว และห้ามลองสูตรคำสั่งแบบอื่นต่อหลังจากการตรวจสำเร็จแล้ว ภาษาที่ใช้ระหว่าง planner↔worker (ทั้ง task ที่สั่งและรายงานที่ส่งกลับ) ต้องเป็นภาษาอังกฤษเสมอเพื่อลด token ไม่ว่าจะพูดภาษาใดกับผู้ใช้ (CHANGE-024)

REQ-018 — การประกอบ role prompt ต้องรักษา repository requirements และ custom context ไว้ ไม่ตัด section หรือบรรทัดที่ไม่เกี่ยวข้องออกด้วยการจับคู่ชื่อ tool แบบ heuristic ขอบเขต role ของ Main Agent ต้องมีผลเหนือคำสั่ง direct-execution ที่ขัดแย้งกันใน context ที่ได้รับมา และค่าเริ่มต้นของ CLI/SDK ที่สร้างในตัวต้องไม่ขัดแย้งกับ role ที่ได้รับมอบหมาย

 REQ-019 — (แก้ไขด้วย CHANGE-025, CHANGE-034) `delegate_to_subagent`, `follow_up_subagent`, `continue_subagent` ต้องคืน control ให้ Main Agent ทันทีพร้อม job id เพื่อ Main ไม่ค้างและรับข้อความใหม่ได้ ระหว่าง worker รัน orchestration ต้องส่ง progress report เข้า Main เป็น continuation turn แบบ hybrid milestone บวก anomaly-gated (milestone tools: write_file/edit_file/bash, anomaly: error สองครั้งติด, backstop: ครบ X tool calls นับจาก report ล่าสุด โดย X จาก config `sub_agent.report_every_tool_calls` ค่าเริ่มต้น 20 และจำกัดไม่เกิน MaxMidJobReports ครั้งต่อ job ค่าเริ่มต้น 3; report เป็น delta เฉพาะ tools ใหม่นับจาก report ล่าสุดพร้อม 1-line status header และตัด result excerpt ที่ 300 runes) ให้ Main ตรวจ scope ว่าขาดหรือเกิน — ถ้าเกิน/ออกนอกขอบเขตให้ `stop_subagent` (blocking) แล้ว `follow_up_subagent` งานใหม่ใน session เดิม; ถ้าตรง scope ให้ตอบสั้นแล้วรอต่อ เมื่อ job ถึง terminal state ต้องส่ง final handoff report เป็น continuation turn เช่นเดิม: `delegate_to_subagent`, `follow_up_subagent`, `continue_subagent` ต้องรอจน job ถึง terminal state แล้วส่งรายงานครบถ้วนกลับเป็น tool result เดียว (สถานะ, step, worker session, ประวัติ tool ทุกชิ้นพร้อม arguments/รายละเอียดและผลลัพธ์รวม error flag, ข้อความสรุปสุดท้าย) โดยค่าของแต่ละ tool result ในรายงานต้องถูกจำกัดความยาวเพื่อไม่ให้ history บวม — Main Agent ห้ามต้องเรียก tool ใดเพื่ออ่านผลซ้ำ และไม่มี tool สำหรับ polling status/history อีก ผลลัพธ์ต้องถูกส่งให้ Main Agent ตรวจสอบเท่านั้น ห้ามรับหรือเลื่อนแผนต่อโดยอัตโนมัติ Main Agent ต้องอ่านรายงานที่ส่งมาในมือ ตรวจสอบความสำเร็จ และยอมรับ step อย่างชัดเจนผ่าน `accept_subagent_result` พร้อม verification evidence การ review จำกัดอยู่ที่สรุป, ประวัติ tool, validation evidence เท่านั้น ไม่นับ raw file content หรือ large binary payload ผลลัพธ์ที่ worker สร้างไฟล์ส่งต่อเป็น file reference พร้อมชื่อ/ชนิด/ขนาดเท่านั้น งานที่ล้มเหลว/หยุด/ไม่สมบูรณ์ retry ต่อใน worker session เดิมผ่าน `follow_up_subagent` ได้ และงานใหม่สั่งต่อเข้า worker session เดิมผ่าน `continue_subagent` โดยคงประวัติเดิม (CHANGE-022)

REQ-020 — การ delegation ต้องจอง running job ได้พร้อมกันไม่เกินหนึ่งรายการต่อ parent session โดยครอบคลุม investigation, planned work, follow-up และ continue Job ต้องเก็บ plan revision และ step identity การ completion, retry, continue และ acceptance ต้องตรวจสอบ transition และห้ามเปลี่ยนแผนใหม่ที่เข้ามาแทนที่ History, stop, follow-up, continue และ acceptance ต้องตรวจสอบ ownership ของ parent History ของแต่ละ job ต้องแสดงรายการ tool ที่ worker ใช้พร้อมชื่อ, arguments/รายละเอียด และผลลัพธ์ (รวมสถานะ error) ของแต่ละ tool นอกเหนือจากข้อความสรุปและผลลัพธ์สุดท้าย Continue ต้อง reuse worker session เดิม (workerID/session database เดิม) สำหรับงานใหม่ได้แม้ job ก่อนหน้าจะถูก accept แล้ว โดยต้องไม่มี running job ซ้อนกันและต้องผูกกับ plan step ปัจจุบันหรือเป็น investigation เมื่อแผนเสร็จแล้วต้องยังสามารถทำ investigation หรืองานต่อเนื่องสำหรับงานใหม่ได้โดยไม่ล้างหรือข้ามงานที่กำลังทำอยู่ `stop_subagent` ต้องเป็น blocking call: ยกเลิก job แล้วรอจน terminal state จริง จึงคืนรายงานสุดท้าย (สถานะ stopped + ผลลัพธ์/ความคืบหน้าที่มี) กลับเป็น tool result ห้ามตอบ "ขอหยุดแล้ว" โดยแจ้งผลภายหลัง และการ cancel ของ parent turn ระหว่างรอต้องหยุด worker และคืนรายงานสถานะ stopped (CHANGE-022)

REQ-021 — (แก้ไขด้วย CHANGE-025) Continuation turn ที่ฉีดเข้า parent มีได้สองชนิดเท่านั้น: progress report (ทุก X tool calls) และ final report เมื่อ job จบ (ห้ามมี event ชนิดอื่นเช่น tool started/running); delegation call คืนเฉพาะ ack พร้อม job id; trace ของ worker ยังต้อง display ผ่านเส้นทางเดิมโดยรักษา routing identity (`channel_id` metadata) ของ input ที่เริ่มต้น turn ไว้เหมือนเดิม reservation/revision ของ orchestration เป็นแบบ process-local และการ persist session/cancellation behavior เดิมต้องไม่เปลี่ยน (CHANGE-022)

REQ-022 — Discord ต้องแสดง canonical response text เป็น Markdown ที่อ่านง่าย ไม่ใช่ SDK output ที่ serialize เป็นข้อมูลดิบ Progress ต้องกระชับ และไม่แสดง raw tool arguments/results, delegated task text, reasoning text หรือ internal planning/review chatter แต่ยังคงแสดง operation label ที่ปลอดภัย, ตัวบ่งชี้ความล้มเหลว, เวลา retry, usage และเวลาที่ใช้ได้อย่างมีประโยชน์ การ render ของ transport ต้องอยู่ใน Discord module ข้อความ progress/response ทั้งหมดของ transport ต้อง render แบบ Components V2 (Container + TextDisplay พร้อม `MessageFlagsIsComponentsV2` ทุก send/edit) ห้ามสร้าง embed ใหม่ (CHANGE-022)

REQ-023 — Discord final และ streamed response text ต้องแบ่งหน้าแบบ lossless ที่ขอบเขต Unicode code point ภายในข้อจำกัด message/embed โดยนับ supplementary characters เป็น UTF-16 units อย่างระมัดระวัง ต้องคง whitespace ที่ขอบเขตไว้ และเมื่อมี fenced code block ต้องปิด/เปิด fence สำหรับการแสดงแต่ละหน้าโดยไม่ลบ content ต้นฉบับ Streaming update ต้องแก้ไขหน้าที่มีอยู่ และ terminal response trace ต้องไม่ replay content ที่ถูก stream ไปแล้ว Progress สามารถเป็น summary ที่มีขอบเขตได้ แต่ response text ต้องไม่ถูกตัดทอน

REQ-024 — Discord text/progress transition ต้องส่งต่อ flush failure และเก็บ buffered state ที่ยังไม่ได้ส่งไว้เพื่อ retry แทนการ reset เมื่อส่ง page สำเร็จต้องบันทึกไว้เพื่อไม่ให้ retry ส่งซ้ำ Success/error terminal path ต้องหยุด live footer update, พยายาม flush buffer ที่ค้าง และล้าง retry-status แม้ operation อื่นจะล้มเหลว และต้องแสดง display error ให้ผู้ใช้เห็น โดยยังคงใช้ trace throttling/cooldown เดิม และ reset/close ต้องยกเลิก timer ที่รออยู่ คำสั่ง interaction ที่ต้องทำงานที่ใช้เวลา (สร้าง channel, โหลด model catalogue, บันทึก settings, อ่านรายการ session) ต้อง defer interaction response แบบ ephemeral ก่อนเริ่มงาน แล้วส่งผลลัพธ์หรือข้อผิดพลาดทาง followup เพื่อไม่ให้ interaction หมดอายุภายใน 3 วินาที ข้อยกเว้นคือการเปิด modal ซึ่งต้องตอบทันทีเพราะ Discord ไม่อนุญาตให้เปิด modal ต่อจาก deferred response

REQ-025 — Transport ที่รับไฟล์ (Discord attachment) ต้องดาวน์โหลดไฟล์นั้นแล้วแปลงเป็น file reference ใน file store และแนบ reference ผ่าน `Input.Metadata` โดยไม่เปลี่ยน canonical Turn/ContentPart contract และต้องคง session routing identity กับ metadata เดิมทั้งหมดไว้ รวมถึง `channel_id` ของต้นทาง ข้อความที่มีเฉพาะ attachment ต้องไม่กลายเป็น turn ว่าง

REQ-026 — Worker agent ต้องมี tool สำหรับอ่านไฟล์จาก file store ภายใน root ที่จำกัดด้วย safePath/withinRoot discipline ของ module tool นั้น แล้วสรุปเนื้อหาและสถานะกลับให้ planner ส่วนการส่งไฟล์ออกแบบจริงต้องอยู่ใน transport module เท่านั้น และห้ามส่ง raw bytes หรือ base64 ผ่าน canonical SDK text path

REQ-027 — Discord ต้องมีคำสั่ง `/new` สำหรับสร้าง text channel ใหม่ใน guild เดียวกับช่องที่เรียกคำสั่ง โดยตั้งชื่อช่องจากวันที่และเวลา (รูปแบบ `ai-YYYY-MM-DD-HHMM`) และคัดลอก model settings ของ session ต้นทาง (provider, model, temperature, thinking level, API key pool index) ไปยัง session ของช่องใหม่ทั้งหมด เมื่อสร้างสำเร็จต้องส่งข้อความสรุปการตั้งค่า (provider/model/thinking/temperature/API pool) เข้าไปในช่องใหม่ กรณีเรียกนอก guild, session ต้นทางยังไม่มี model settings หรือสร้างช่องไม่สำเร็จ ต้องตอบกลับแบบ ephemeral ในช่องเดิมโดยไม่สร้าง session ใหม่ พฤติกรรมทั้งหมดอยู่ใน Discord module และห้ามเปลี่ยน core orchestration, persistence หรือ canonical contract

REQ-028 — Discord คำสั่ง `/model` ต้องเปิด control panel แบบ Components V2 ในข้อความปกติข้อความเดียว (regular message ไม่ใช่ ephemeral เพราะแก้ไขไม่ได้) แล้วแก้ไขข้อความเดิมทุกครั้งที่มีการกด โดยทุก control บันทึกผลทันที ไม่มี staging ข้อความประกอบด้วย Container กล่องเดียว (accent bar เดียวกันทั้งกล่อง: หัวข้อ ค่า settings แยกฝั่ง Main/Sub แบบ plain text ไม่มีอิโมจิ แล้วตามด้วย controls ทั้งหมดในกล่อง ทั้งปุ่มและ select menu ผ่าน ActionRow) ได้แก่แถวปุ่ม Main/Sub ต่อด้วย select menu provider (ไม่ preselect), select menu model (ไม่ preselect), แถวปุ่ม Thinking/Temp, select menu API pool และปุ่ม Save สีเขียวล่างสุดซึ่งกดแล้วถอด controls ทั้งหมดออกเหลือสรุปอย่างเดียว (freeze) ปุ่ม Thinking/Temp ใน container กดแล้วเปิด modal ให้เลือก thinking จาก select menu และกรอก temperature เป็นตัวอักษร (default หรือ 0.0–2.0) เมื่อ submit ต้องบันทึกแล้วแก้ไข panel ข้อความเดิม มีเส้นคั่นระหว่างฝั่ง Main/Sub อิโมจิมีเฉพาะในปุ่มและเมนูเท่านั้น สรุปเป็น plain text เมื่อ provider หรือ model catalogue มีรายการเกิน 25 ให้แบ่งหน้าในตัวเลือกเองโดย `Next` อยู่ด้านบนเสมอ (หน้าแรก `Next` + 24 รายการ หน้ากลาง `Previous` + `Next` + 23 รายการ หน้าสุดท้าย `Previous` + รายการที่เหลือ) และชื่อเมนูต้องบอกหน้าปัจจุบัน (เช่น `Select model (1/2)`) select menu ทุกเมนู (provider/model/API pool) ไม่ preselect ค่าปัจจุบันดูในสรุป การเปลี่ยน provider ต้องคง model เดิมไว้ถ้ายังอยู่ใน catalogue ไม่เช่นนั้นใช้ model แรกของ catalogue เพื่อให้ session ใช้งานได้เสมอ controls ทุกตัว (รวม modal thinking/temperature) อ่านและบันทึก settings ของฝั่ง active เท่านั้น การสลับโหมดต้องรีเซ็ตหน้า model มาที่ model ของฝั่งนั้น

REQ-029 — Session ต้องจำ agent mode (`main` หรือ `sub`, ค่าเริ่มต้น `main`) แบบ persist โหมด `main` ทำงานแบบ planner เดิม (planning prompt + เครื่องมือ orchestration ไม่มี execution tools) โหมด `sub` ทำงานแบบ worker ตรง (execution tools เต็ม ไม่มี planning wrapper) โดยไม่ต้องพึ่ง global `DisablePlanning` switch การสลับโหมดต้องมีผลกับ turn ถัดไปของ session นั้นทันที

REQ-030 — แต่ละ Discord channel มีสอง persistent sessions แยก db กัน: main (`discord:channel:<id>`) ทำงานแบบ planner, sub (`discord:channel:<id>:sub`) ทำงานแบบ worker โดยแต่ละ session เก็บ settings ของตัวเอง (provider, model, thinking level, temperature, API key pool index) ใน top-level fields ไม่มี overlay gateway ต้อง route ข้อความของ channel ไป session ตามโหมด active ที่จำไว้บน main session (default main) sub session ต้อง reuse ได้ตลอดจนกว่าจะลบ การเข้า sub ครั้งแรกที่ยังไม่มีค่าต้อง seed จากฝั่ง main `/new` ต้องคัดลอกทั้งสอง sessions พร้อมโหมด

REQ-031 — Discord progress trace ของ Main Agent และ Sub-agent render เป็น Components V2 โดยแต่ละ actor ได้ข้อความของตัวเองพร้อม accent สีแยกกัน (planner blurple, worker เขียว) ภายใน actor แก้ข้อความเดิมแบบ in-place เสมอ ห้ามใช้ embed ใหม่ ลำดับข้าม actor ต้องถูกต้องตามเวลาจริง: transport ต้องนับลำดับข้อความที่ created ต่อ channel ถ้ามีข้อความใด (ของ actor ไหน หรือข้อความ response text) ถูกสร้างต่อหลังข้อความปัจจุบันของ actor แล้ว บรรทัดใหม่ของ actor นั้นต้องเปิดข้อความ segment ใหม่ด้านล่าง ห้าม append บรรทัดใหม่ลงในข้อความที่เก่ากว่าข้อความล่าสุด และเมื่อจบ turn ต้องปิดข้อความเดิม (completed) ข้อความถัดไปเริ่มใหม่ (CHANGE-023)

REQ-032 — Trace ต้องแสดง tool ทุกตัวที่เรียกจริงใน turn นั้น ไม่ซ่อน orchestration tool ใด (`plan`, `stop_subagent`, `accept_subagent_result`, `delegate_to_subagent` ฯลฯ ต้องเห็นเป็นบรรทัด) แต่ละบรรทัด tool ต้องแสดงชื่อ, สถานะ, เวลา และ arguments ของ tool แบบ one-line ที่ตัดทอนความยาวปลอดภัย (ค่า argument เป็นสิ่งที่ transport ยอมรับให้แสดงได้ตั้งแต่ CHANGE-023) ส่วน raw result ของ tool, delegated worker task text, reasoning text และ internal chatter ห้ามแสดง และการดำเนินของ worker ระหว่าง delegation ต้องเห็นใน trace เรียงตามเวลาที่ emit จริง (CHANGE-023)

REQ-035 — Execution tool ของ shell ต้องชื่อ `bash` และรับ shell command line ตรง ๆ เป็นสตริงเดียว (ไม่มี args array แยก, ไม่มีข้อจำกัด multi-word) รันผ่าน bash ใน workspace พร้อม timeout และ process-tree kill like เดิมของ `run_command`; คำสั่ง long-running เดิม (`run_job`/`check_job`/`close_job`) คง behaviour เดิม (CHANGE-024)

REQ-036 — Role ของ Main Agent คือ planner ไม่ใช่ผู้ส่งต่อ: ห้ามส่งข้อความดิบของผู้ใช้เป็น task ของ worker ตรง ๆ — ต้องแตกงานเป็นขั้น, เขียน task เป็นภาษาอังกฤษที่มีบริบท/ขอบเขต/เกณฑ์ตรวจยืนยันกำกับ, และตรวจสอบรายงานก่อน accept ทุกครั้ง (CHANGE-024)

REQ-037 — เมล trace ที่ actor ใดมีบรรทัด "provider accepted" ค้างอยู่เมื่อ content มาถึง: ถ้า container นั้นมีเฉพาะบรรทัด accepted อย่างเดียว ให้แปลงข้อความนั้นเป็น response content โดยตรง (edit ในที่, ไม่สร้างข้อความใหม่) ถ้ามีบรรทัดอื่นอยู่ด้วย ให้ลบบรรทัด accepted ออกจาก container แล้วส่ง content เป็นข้อความใหม่ตามลำดับ (CHANGE-024)

REQ-033 — ตัวจับเวลาใน trace ต้องวัดจากช่วง `sending request to provider` จน tool execute สำเร็จจริง ด้วยการลบกันของ Unix millisecond timestamp ที่บันทึกไว้ ณ แต่ละ event (แบบเดียวกับ turn footer) ไม่ใช่ `time.Since` ณ ตอนรับ event ฝั่ง display; บรรทัดที่ยัง exec ไม่จบแสดงเวลาสะสมตั้งแต่ request นั้น และ tool ที่เสร็จแล้วแสดงเวลาตั้งแต่ส่ง request จน exec สำเร็จ; ตัวบ่งชี้ "provider accepted" ต้องรวมอยู่ในกลุ่ม display ของ request/tool เดียวกัน ห้ามเป็นบรรทัดอิสระที่ค้างอยู่เมื่อ tool เริ่มทำงาน (CHANGE-022)

REQ-034 — Plan ต้องใช้งานได้จริงเป็น checklist ของ Main Agent: (1) checklist พร้อมสถานะของแต่ละ step ต้องถูก inject เข้า system prompt ของ planner ทุก iteration เพื่อให้ Main มองภาพรวมโปรเจคตลอดโดยไม่อ่าน history เอง (2) sub-agent ทำงานย่อยทีละ step ตามแผน (3) delegation คืน job id ทันที และ Main ได้รับรายงานเองโดยอัตโนมัติ — progress ทุก X tool calls และ final report ครบ (terminal status, final result, validation evidence, สรุปของ worker) ตอนงานจบ ไม่มี tool polling status/history (ลด API call) (4) `stop_subagent` เป็น blocking เช่นกัน: รอจน worker หยุดจริงแล้วคืนรายงานสุดท้าย (stopped + ความคืบหน้า/tool history) ในผลตอบเดียว ห้าม "สั่งหยุดแล้วแจ้งผลทีหลัง" (5) เครื่องมือ orchestration ที่เหลือ (`accept_subagent_result`, `follow_up_subagent`, `continue_subagent`, `plan`) คง semantics เดิม (CHANGE-022)

REQ-038 — Discord ต้องมีคำสั่ง `/workspace <path>` สำหรับเลือกตำแหน่งทำงานของ channel นั้น (appplied กับทั้งสอง sessions main+sub) โดยรองรับ `~/` และ `~` (expand เป็น home directory ของ user ที่รัน daemon), ต้องเป็น path ที่มีอยู่จริงและเป็น directory เท่านั้น (ไม่สร้างใหม่), บันทึกแบบ persist ใน session (คอลัมน์ `workspace`) และมีผลกับ tool ทุกตัวที่resolve root ต่อ invocation ตาม session ของ turn นั้น (main turn, sub-mode turn, และ worker ที่ delegate ออก) — session ที่ไม่มีค่าใช้ global workspace เดิม; เรียกโดยไม่ใส่ path ต้องแสดงค่าปัจจุบันพร้อม status; ผลตอบเป็น ephemeral ใน channel; `/new` ต้องคัดลอก workspace ไป channel ใหม่ด้วย (CHANGE-025)

REQ-039 — (แก้ไขด้วย CHANGE-030) Adapter `opencode` ต้องยิง `/responses` ก่อนแล้วตกไป `/chat/completions` เมื่อ endpoint นั้น serve โมเดลไม่ได้ (404, 400 `model_not_supported_on_endpoint`, หรือ 500 — ตรวจ live แล้วว่า Zen แยกโมเดลตาม endpoint ทั้งสองทิศ: spark ใช้ได้เฉพาะ `/responses`, mimo ใช้ได้เฉพาะ `/chat`) โดย 401/403/429 ต้อง return ทันทีไม่ fallback; ทุก request พร้อม fingerprint ของ opencode ตัวจริงที่ตรวจจาก binary บนเครื่อง (v1.18.31): `User-Agent: opencode/<version>` (ค่าเริ่มต้นคือเวอร์ชันที่ตรวจพบ), `HTTP-Referer: https://opencode.ai/`, `X-Title: opencode` และ `x-opencode-session: <ses_-id>`; ses_-id ทรง `ses_f<hex 8 ตัว>ffe<สุ่ม 14 ตัวอักษร A-Za-z0-9>` โดย hex ลดตามเวลาขึ้น (time-descending แบบ opencode) ถูก mint ครั้งเดียวต่อ harness session แล้ว reuse ตลอด process ผ่าน cache ใน memory; custom headers จาก provider config ชนะค่าเริ่มต้นของ UA/Referer/Title ได้แต่ชนะ session header ไม่ได้ (session header เป็นของ adapter เสมอ); body ต้องไม่มี `user` field (ตรงกับ opencode ที่ส่ง session ผ่าน header เท่านั้น); BaseURL ค่าเริ่มต้น `https://opencode.ai/zen/v1`; ListModels ใช้ `GET /models` จริง (คง REQ-007); เลือก adapter ผ่าน `"adapter": "opencode"` แบบ explicit เท่านั้น ไม่เปลี่ยน name inference เดิม (`opencode` ยัง infer เป็น anthropic); RouterClient ต้อง stamp `Request.SessionID` จาก session ทุกครั้งก่อนส่งให้ provider (CHANGE-026)

REQ-040 — Provider HTTP ทุกเส้น (DoJSON/SSE ส่วนกลาง) ต้องส่ง `User-Agent` เริ่มต้น (`ai`) เมื่อ adapter ไม่ได้กำหนดมาเอง — gateway บางราย (เช่น NousResearch ผ่าน Cloudflare) ปฏิเสธ `Go-http-client` ด้วย 403 HTML ทำให้ discovery ล้มเหลว; header ที่ adapter/config ระบุไว้ชัดต้องชนะค่าเริ่มต้นเสมอ (คง REQ-039 ที่ UA ของ adapter opencode ยังมีผลเหนือ) และการตอบ interaction ของ Discord ที่รายงาน provider error ต้องถูกตัดให้สั้นกว่าขีดจำกัด 2000 ตัวอักษรของ Discord เสมอ (log ฝั่ง daemon เก็บข้อความเต็ม) มิฉะนั้นผู้ใช้จะไม่เห็นสาเหตุจริง (CHANGE-027)

REQ-041 — Discord ต้องมีข้อความสถานะถาวรแบบ tool-call-only ต่อ user turn เป็น Components V2 container เดียว: แสดงเฉพาะ tool calls ล่าสุดไม่เกิน 10 รายการ แต่ละบรรทัดมีชื่อ tool + ok/error + วินาทีที่ใช้เท่านั้น ห้ามมี working/retrying text, args dump, result excerpt, token footer รายวินาที หรือเนื้อหา sub-agent; edit ข้อความเดิมแบบ in-place ทุก tool event ด้วย throttle ไม่เกิน 1 ครั้งต่อ 3 วินาที (ใช้ heartbeatThrottleMs เดิม ส่ง Channel typing ระหว่าง edit ห้าม ticker รายวินาที ห้ามส่ง progress message ใหม่); status send/edit ต้องติด `MessageFlagsSuppressNotifications` ส่วน final answer คง ping behavior เดิม; เมื่อจบ turn ให้ยุบเป็น receipt บรรทัดเดียวเพียงครั้งเดียว; คง V2 path, pagination, accent colors, routing เดิม (CHANGE-036)
